# Gotchas

Non-obvious traps. One file per trap in `gotchas/`. A flat list.

- [[a-new-quota-source-is-cheapest-to-validate-against-one-already-trusted]] — proving a new quota endpoint "really moves" is the expensive *and* weak method: the Anthropic usage endpoint carries a multi-minute 429 penalty (so #204 capped the spike at 2–3 reads per endpoint), and its readings are **integer percents**, so ten minutes of ordinary use cannot move a 5h window by a whole point — "identical across two reads" is indistinguishable from "static ceiling" at that resolution. #204's two spaced reads did return the same `42`/`71`, and that observation alone proves nothing. The cheap move is **cross-source agreement**: `~/.wisp/status.json` already holds meters the Bridge wrote from live turn headers, and the endpoint matched them exactly (Anthropic 5h `42%` / 7d `71%`, resets agreeing to the second; Codex 7d `100%` at `reset_at 1787198654`). Since the header meters are known to move, exact agreement makes the endpoint the same live ledger and clears [[2026-07-30-an-advertised-ceiling-that-never-decrements-is-not-a-meter]] for free. Free secondary tell: **timestamps that drift in the sub-second digits across two reads mean the response is recomputed per call**, not a cached blob. Does not retire [[a-cancelled-response-body-cannot-test-whether-a-counter-decrements]] — that one governs *header* recon on a turn, this one *endpoint* recon where there is no body to drain and no budget to repeat
- [[the-usage-payload-names-most-of-its-buckets-in-unstable-codenames]] — `api.anthropic.com/api/oauth/usage` returns readable `five_hour` / `seven_day` and then a drift field of mostly-`null` named buckets: `seven_day_opus`, `seven_day_sonnet`, `seven_day_cowork`, `seven_day_oauth_apps` plus unreleased-feature codenames (`tangelo`, `iguana_necktie`, `nimbus_quill`, `omelette_promotional`, `cinder_cove`, `amber_ladder`) that will be renamed or removed without warning. **Parse the `limits[]` array instead** — normalized `kind`/`group`/`percent`/`severity`/`resets_at`/`scope`/`is_active`, and it is the only place the model-scoped weekly window appears at all (`kind: "weekly_scoped"`, `scope.model.display_name`). Same family of bug as the header recon's near-miss, which is why `ANTHROPIC_WINDOW` matches on **shape** rather than names. Two riders: **units differ from the header path** (integer percent + ISO-8601 here vs 0..1 fraction + epoch seconds in `status.json`, which #203's `expired()` depends on — normalize at the boundary or the sources land 100× apart), and **both payloads carry account identifiers** (Codex returns `email`/`user_id`/`account_id`; Anthropic returns an org uuid and workspace id in *response headers*) — redact on values
- [[a-branch-cut-from-an-unpushed-main-sweeps-it-into-the-squash]] — local `main` drifts ahead of `origin/main` on this repo *by convention* (`.context/` commits land on main and step 8 says don't push), so a `git log` that looks synced routinely isn't. A ticket branch cut from that main inherits the unpushed commits, GitHub diffs against `origin/main` which lacks them, and the **squash-merge collapses them all into one commit wearing the ticket's subject**. Live on #202: main was 4 commits ahead (`4315455`, `2705bac`, `e31c92d`, `9a4b797`), and `3465c7c` landed as an 18-file "wisp log" commit of which 5 files were the ticket. **Nothing is lost** — the remote gets the union — but history granularity is: `2705bac`'s statusline fix no longer stands alone, so a later `git log <tag>..main -- <path>` **Surfaces derivation reads a feat commit where a fix belonged**. Guard is one command *before* cutting: `git rev-list --left-right --count origin/main...main`, right-hand number must be 0. Don't fix it after by rewriting published history — force-pushing a public default branch is the maintainer's call. Second half: `gh pr merge --squash --delete-branch` then aborts with `fatal: Not possible to fast-forward` and leaves the tree **looking reverted** (edited files read as their old selves, greps for the new symbol miss); it isn't — verify with `git diff --stat origin/main main`, then `git reset --hard origin/main`
- [[a-picked-alias-reaches-the-statusline-prefixed-claude-wisp]] — an Alias is named `keemee` and `wisp routing` prints `keemee`, but **nothing a user picks ever says `keemee`**. Claude Code's `/model` list IS the Bridge's Anthropic door, which prefixes every row `claude-wisp-<id>` so the picker lists it at all (`bridgeAnthropic.ts:676`); the choice is stored verbatim (`~/.claude/settings.json` → `"model": "claude-wisp-keemee"`). The door strips its own prefix one line inside the request parser (`bridgeAnthropic.ts:250`) **before** `resolveRoute` sees it — so routing is correct and the strip is invisible to anyone reading `routing.ts`. Any consumer reading the name from **Claude Code** instead starts upstream of that strip: the statusline's alias equality test never matched, and every picked alias rendered a bare `wisp` row (fixed `2705bac`, wisp-slot 1.7.3). Two more shapes ride along — Claude Code appends its own **`[1m]` tier suffix**, and `display_name` is not a fallback (alias rows read `keemee — kimi-k3`). The **family fuzzy hid it for a month** because `includes('opus')` shrugs off both affixes; only the exact-match rungs are sensitive, which is why it presented as "aliases are broken" rather than "the id is not what you think"
- [[kimi-in-a-model-string-names-the-kimi-code-oauth-row-not-opencode-go]] — two things wear the name: Provider `kimi` = **Kimi Code subscription** (OAuth device flow, no key, ever), while the kimi-k2.5/k2.6/k2.7-code/k3 model ids live on **OpenCode Go**. `kimi/kimi-k3` hits the provider-id rung → OAuth row; the user's OpenCode key in the `opencode-go` slot is never read (`bearerFor`'s kimi arm returns `kimiAuth.bearer()` only — the #170 keyFor-seam design). Armed by the error wearing the wrong words: signed-out kimi falls through the keyed tail and says `400 has no API key configured` when the truth is 401 not-signed-in — sent a user key-hunting on 2026-08-03. Want kimi-k* on your key → `opencode-go/kimi-k3`; and never alias `kimi` (provider-id rung outranks alias-exact, it can never win)
- [[a-cancelled-response-body-cannot-test-whether-a-counter-decrements]] — reading a response head then calling `res.body.cancel()` captures headers cheaply and **cannot tell a live counter from a static ceiling**, because an aborted stream may never be billed. Nearly inverted #200: the cancelled pass read `x-ratelimit-remaining-requests: 864` against a limit of `864` on Grok, which looks like "parseable, just untouched". Fully draining (`await res.text()`, byte count logged) and firing **2–3 consecutive turns** showed `864/864` and `8300/8300` never move — advertised ceilings, not readings. One request proves a header exists; only consecutive *completed* requests prove what it means. Draining is not expensive with a one-word reply (~9 KB), so there is no reason to cancel
- [[loadcodeassist-answers-with-the-account-email-inside-it]] — the `loadCodeAssist` call `antigravityAuth.ts:58` makes for the project id returns the signed-in **email** inside `upgradeSubscriptionUri`, **percent-encoded** (`%40`), under a key matching no `email`/`id`/`project` pattern — so a field-name redactor misses it twice. Plus `cloudaicompanionProject`, `currentTier.id`, `paidTier.id`. Redact on the **value** (`@`, `%40`, `gmail`, `wrk_`/`prj_` prefixes) and drop the prose blocks. Same class on opencode: a `401 CreditsError` body names a billing URL carrying the workspace id — quoting it verbatim publishes it
- [[the-statusline-duplicates-resolveroute-and-drifts]] — `plugins/slot/statusline/wisp-statusline.js` runs out-of-process under Claude Code's hook, cannot import `@wisp/core`, and therefore **re-implements** `resolveRoute` (`routing.ts:60-91`) in plain JS where no test can see it. It drifted immediately: the copy knew only the family-fuzzy rung, so an **aliased** route (`sol`, `grok`, `gemini`) resolved to no Target — route row collapsed to the bare word `wisp`, and because the live gate is `status.model === target?.model` (never satisfiable against `undefined`), the previous Provider's reading was the only thing left on screen. Reported as "why is it showing anthropic when I'm on codex"; fixed `f565e94`. **That sentence has two causes — read the route row to tell them apart:** bare `wisp` = resolution (this page), a *named* route beside a foreign quota row = global-slot displacement ([[status-json-is-global-so-it-cannot-observe-another-session]]). Real order: **provider-id → alias exact → family fuzzy (`claude-*` only) → active**; two rungs are still missing. **A wrong-Provider reading is visually identical to a stale one** — both are the dimmed dated row — so suspect resolution, and check whether the picked model is an alias, before suspecting the ledger. Run `node plugins/slot/statusline/check.js` after touching either side (**20 assertions**, real script, sandboxed `WISP_HOME`; each fix control-verified against its own pre-fix file — 5/10 for `f565e94`, 4 of the 10 added for the displacement fix)
- [[relay-legs-on-this-repo-must-spawn-native-claude]] — three settings in `.claude/relay/ticket-loop.md` that look like defaults and are not. **`binary: claude` is deliberate** — a `claude-wisp` leg dies at boot with no Bridge on 41184, and this repo's tickets edit Bridge code so a leg must not route through what it is changing; the skill's auto-detection picks `claude-wisp` in this repo every time, so the explicit field must stay. **`'queue empty'` needs single quotes** — double quotes shred the cmd spawn. And **`stop: true` means the next invocation RE-INITIALIZES, not resumes**: the skill reads Handoff/Breadcrumbs only when `stop: false`, so a "preserved across re-seeds" heading is a note-to-self, not a mechanism — anything that must survive belongs in `gotchas/`. Init also fires when the `body:` field does not match the typed command **exactly**, so keep `body:` to plain `/preset ticket-loop` (every augmentation people add is already in the preset's steps 1 and 8)
- [[a-sandboxed-live-check-dies-by-port-not-by-pkill]] — the live-turn check runs in a `mktemp -d` `WISP_HOME` with `auth.json` **copied** in (never read in place — refresh writes back), a BOM-free `config.json`, and a spare port, so refreshed tokens, the bridge secret and the global `status.json` all land in the sandbox instead of the real store. The trap is teardown: `pkill -f "index.tsx serve"` did **not** kill the sandbox host, and a broader pattern would kill the real Bridge the session depends on. Find it **by port**, stop that pid, then confirm 41184 is still alive — teardown is not done until the real Bridge is re-verified
- [[an-empty-quota-ledger-is-usually-correct-not-broken]] — `status.json`'s `providers` map deliberately **excludes the Provider serving the current turn** (it *is* the top-level snapshot), so on a machine where one Provider serves everything the map is absent forever and the statusline shows no remembered rows — indistinguishable from a ledger that is never written. Bit this minutes after cutting 2.0.42: release installed, Bridge restarted, snapshot zero minutes old with live meters, `providers: null` — because every turn had been `opus → anthropic`. Check `routing.families` in `config.json` first: if every family used so far points at the same `providerId`, an empty map is the *only* correct answer, and one turn on a differently-routed family creates the entry. Two neighbours: **quota only arrives on a response head** (no poll, no CLI — an unspent Provider's limits are simply unknown), and **only two wires report at all** — `codexClient.ts` and `anthropicClient.ts` wire `onQuota`, `xaiClient.ts` and `antigravityClient.ts` do not, so Grok and Antigravity never appear no matter how many turns they serve Third neighbour: **codex on a Plus plan has ONE window** — `x-codex-primary-window-minutes: 10080` (7d) with `secondary` at `0`, so a codex session renders a single `7d` row and a `5h`/`7d` **pair is Anthropic**, which is the tell for the displacement bug
- [[a-live-negative-on-this-wire-is-usually-the-fixture-or-the-model]] — the converse of the CRLF lesson, and it cost #191 two diagnosis cycles in one run: a live **failure** reads as authoritative and usually is not. A first vision check returned `Antigravity API error 400: Unable to process input image` — which reads exactly like "this wire refuses vision", contradicting #186 — but the payload was correct and the **fixture** was a 156-byte base64 blob typed to *look* like a PNG; re-run against a real file (`docs/claude-model-picker.png`) and the model describes it accurately. Separately, `gemini-3.1-pro-low` answered the same tool prompt with `stop=end_turn, calls=[]` on two runs and a real `tool_use` on a third — a **model choice**, with the declarations on the wire the whole time (confirmed by capturing the request body); `gemini-3-flash` called first try, every try. The rule: a live negative has three candidate causes and the door is the **least** likely — your fixture, the model's discretion, then the code. Capture what actually went out (a two-line `globalThis.fetch` wrapper prints the body without disturbing the client) and re-run with a known-good input before believing the wire. A 400 naming the *input* (`INVALID_ARGUMENT`, "unable to process") points at your bytes. And a **non-deterministic criterion needs retries in the probe** — one sample would have recorded "tool calling does not work" on a wire where it demonstrably does
- [[the-anthropic-door-does-not-use-the-executor-records]] — #167 unified the **OpenAI** door onto one `ProviderExecutor` record per kind and left the **Anthropic** door alone: `startProviderStream` still carries its own hand-written chain (codex → anthropic → xai → keyed) and never consults `providerExecutors`. So **adding a record does not add a Provider to `/v1/messages`** — #189 added the Antigravity record and wired one door; on the other the same Provider falls through to the keyed tail and answers `400 has no API key configured`, which reads like a config mistake and is a missing arm (found by #190 writing a two-door 429 test). **#191 (`915d415`) added that arm — the chain is now codex → anthropic → xai → antigravity → keyed — and the rule is the durable part of the page, not the gap.** What IS shared is the **failure answer**: both doors call the one `failProviderRequest`, which reads `executorFor(provider).classify`, so #191 inherited the 429 without re-implementing it. What is NOT shared is request shaping — the door owns the #139 split, the #156 chain, vision/documents and non-strict tools, which is why #167 left it alone, so a new arm is **per-wire, not a copy of its neighbour** ([[2026-07-30-the-antigravity-arm-is-not-a-copy-of-the-anthropic-arm]]). The rule: a new Provider kind means **two** places, and missing the second is silent on the OpenAI door and unit-invisible — only driving the *other* door catches it
- [[the-wisp-badge-runs-from-the-repo-checkout-not-the-plugin-cache]] — `~/.claude/hooks/statusline-wrapper.ps1` points the wisp badge at the **repo checkout** (`plugins/slot/statusline/wisp-statusline.js`), deliberately, because the plugin cache path is per-version. So a stale `~/.claude/plugins/cache/wisp-router/wisp-slot/<v>/` is **irrelevant to the badge** and `/plugin update` does not change what the statusline runs. Cost a session: the 1.5.0 cache was correctly seen to lack the `status.json` reader, and the wrong conclusion ("the badge won't appear until the user updates") rode in the handoff note as a blocker while the badge was working the whole time. Read the wrapper first to find which file actually runs, then test that file. It exits 0 **silently** unless both `ANTHROPIC_BASE_URL` is set and `$WISP_HOME` exists — an unbridged shell renders nothing, identical-looking to broken
- [[verifying-a-fix-release-needs-the-previous-version-as-a-control]] — "install the new version, bug is gone" proves nothing: most natural checks pass on the **broken** version too, so green means the harness ran, not that the fix shipped. On #183 a *read* check was green on 2.0.38 and 2.0.39 alike — the read never threw, it returned `{}` with exit 0; the bug was in the **write**. Run the identical harness against the **previously published** tarball (`npm i wisp-router@<prev> --prefix …`) and require it to FAIL. Design it around the mutation: touch a *different* row than you seed, and seed unrelated top-level fields so the blast radius shows. Also here: npm can **404 a version its own publish job just succeeded on** — propagation lag, not a broken release; check the job log and `dist-tags`, then retry
- [[a-handoff-cannot-predict-a-queue-state-its-own-last-step-changes]] — a relay leg writes its handoff **before** the next leg runs, so any claim about "what the queue will look like afterwards" is a prediction — and when the leg's own last step **mutates the queue**, it is a prediction written from a state that no longer exists. Leg 6 → 7 shipped both halves in one pass: *"8. Label #197 `ready-for-agent` — last act"* immediately followed by *"then the queue is dry again → `stop: true`, no leg 8"*. Step 8 arms a ticket, so the queue contains exactly what step 8 just added; each half reads as correct alone and only the **ordering** is wrong. Write the stop as an **instruction with its reason**, never as a prediction of queue state. Leg 7 honored the stop because the *reason* outlived the premise (the vsix is packaged, not installed — the extension face has a human step regardless of the label), and pointed the baton at #197 so re-arming costs one command. When an instruction and its justification come apart, prefer the one whose reason still holds; when neither is clear, take the cheapest to reverse — a stall costs one command, an unwanted autonomous full-permission leg costs a review
- [[status-json-is-global-so-it-cannot-observe-another-session]] — `~/.wisp/status.json` is **one file per machine**, rewritten after every bridged turn on the Anthropic door. If *you* are running bridged, your own tool call overwrites it, so reading it to inspect **another** session returns your own snapshot, one second old and entirely plausible-looking. Cost a step while verifying #165. The statusline's model-match guard hides cross-family clobbering from the badge but does **not** stop the write. To verify a session actually reported usage, read the per-session **Claude Code transcript** instead — folding rows by `message.id`. **It also displaces your OWN reading, which is a rendering bug:** the guard suppresses the wrong snapshot but never goes looking for the right one, so a `sonnet → codex` session beside a constantly-turning `opus → anthropic` one rendered anthropic's windows as its only quota row while its codex reading sat unread in the `providers` ledger. The reader now checks both places by `providerId` ([[2026-07-30-the-statusline-finds-its-quota-by-provider-in-either-of-two-places]]) — any new consumer of `status.json` must do the same
- [[a-bom-in-wisp-config-silently-empties-the-whole-config]] — a UTF-8 BOM at the start of `~/.wisp/config.json` makes Wisp discard the **entire** config (provider, models, effort, the whole Routing map) with **exit 0 and no stderr**: `JSON.parse` throws, `parseObject` swallows it, `parseWispConfig` returns `{}` *above* every field guard. Bites agents because PowerShell 5.1's `Out-File -Encoding utf8` writes a BOM **by default**, so a sandbox `WISP_HOME` seeded from PowerShell reads as empty and looks exactly like a broken feature — it cost a verification pass during the 2.0.38 cut. Check `head -c 3 config.json | xxd` for `efbbbf` before suspecting code. Filed **#181**, pre-existing
- [[harvest-tickets-carry-body-text-blockers-not-native-links]] — the harvest tickets' `## Blocked by` is **prose in the issue body**; the native GitHub dependency links are not set, so GraphQL `blockedBy` returns an **empty list even for a genuinely blocked ticket** (#173 reported empty while three of its four blockers were open). An unattended leg that trusts it will start a ticket whose dependencies have not shipped. Read the body section and cross-check the queue table in [[active-work]]; empty `blockedBy` is *no information*, not *no blockers*
- [[readablestream-error-discards-the-queued-chunks]] — `controller.error()` **empties the queue**, so enqueue-then-error in one tick does NOT model a partial delivery: the reader sees only the error, and a test meant to prove "already delivered ⇒ never retried" silently tests the opposite case. Drive it from `pull()` instead. Tell: `expected 502 to be 200` on a partial-stream test
- [[a-door-commits-its-200-head-before-the-upstream-request-has-run]] — provider streams are async generators, so calling one does NO IO: the doors wrote `writeHead(200)` before the request had fired, making every pre-stream failure a **200 with an empty body** and the 502 branch dead code. `primeStream` (#166) pulls the first event ahead of the head. Tell in a test: `expected 200 to be 502`. **Fixed everywhere by #167** (priming is uniform across all four records) — and that uniformity is what made #168's retry boundary expressible
- [[cc-transcript-rows-are-blocks-not-messages]] — a transcript row is one content BLOCK, not one message: `message.id` / `stop_reason` / `usage` repeat on every row of the same message. Fold by `message.id` first or the file lies three ways — every message looks single-block, `usage` sums N×, and a text-only row appears to violate its own `stop_reason`. Produced a whole false bug report on 2026-07-25
- [[claude-code-can-refuse-a-turn-before-the-bridge-ever-sees-it]] — `Context limit reached` in a bridged session can be a LOCAL Claude Code block that never hit the wire; prove it from CC's own transcript (`~/.claude/projects/<slug>/*.jsonl`) — a ms-scale gap between tool_result and the `<synthetic>` error means no round trip. 2.1.220 also inflates the `/context` Messages row past its own honest headline
