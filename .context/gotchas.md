# Gotchas

Non-obvious traps. One file per trap in `gotchas/`. A flat list.

- [[an-empty-quota-ledger-is-usually-correct-not-broken]] — `status.json`'s `providers` map deliberately **excludes the Provider serving the current turn** (it *is* the top-level snapshot), so on a machine where one Provider serves everything the map is absent forever and the statusline shows no remembered rows — indistinguishable from a ledger that is never written. Bit this minutes after cutting 2.0.42: release installed, Bridge restarted, snapshot zero minutes old with live meters, `providers: null` — because every turn had been `opus → anthropic`. Check `routing.families` in `config.json` first: if every family used so far points at the same `providerId`, an empty map is the *only* correct answer, and one turn on a differently-routed family creates the entry. Two neighbours: **quota only arrives on a response head** (no poll, no CLI — an unspent Provider's limits are simply unknown), and **only two wires report at all** — `codexClient.ts` and `anthropicClient.ts` wire `onQuota`, `xaiClient.ts` and `antigravityClient.ts` do not, so Grok and Antigravity never appear no matter how many turns they serve
- [[a-live-negative-on-this-wire-is-usually-the-fixture-or-the-model]] — the converse of the CRLF lesson, and it cost #191 two diagnosis cycles in one run: a live **failure** reads as authoritative and usually is not. A first vision check returned `Antigravity API error 400: Unable to process input image` — which reads exactly like "this wire refuses vision", contradicting #186 — but the payload was correct and the **fixture** was a 156-byte base64 blob typed to *look* like a PNG; re-run against a real file (`docs/claude-model-picker.png`) and the model describes it accurately. Separately, `gemini-3.1-pro-low` answered the same tool prompt with `stop=end_turn, calls=[]` on two runs and a real `tool_use` on a third — a **model choice**, with the declarations on the wire the whole time (confirmed by capturing the request body); `gemini-3-flash` called first try, every try. The rule: a live negative has three candidate causes and the door is the **least** likely — your fixture, the model's discretion, then the code. Capture what actually went out (a two-line `globalThis.fetch` wrapper prints the body without disturbing the client) and re-run with a known-good input before believing the wire. A 400 naming the *input* (`INVALID_ARGUMENT`, "unable to process") points at your bytes. And a **non-deterministic criterion needs retries in the probe** — one sample would have recorded "tool calling does not work" on a wire where it demonstrably does
- [[the-anthropic-door-does-not-use-the-executor-records]] — #167 unified the **OpenAI** door onto one `ProviderExecutor` record per kind and left the **Anthropic** door alone: `startProviderStream` still carries its own hand-written chain (codex → anthropic → xai → keyed) and never consults `providerExecutors`. So **adding a record does not add a Provider to `/v1/messages`** — #189 added the Antigravity record and wired one door; on the other the same Provider falls through to the keyed tail and answers `400 has no API key configured`, which reads like a config mistake and is a missing arm (found by #190 writing a two-door 429 test). **#191 (`915d415`) added that arm — the chain is now codex → anthropic → xai → antigravity → keyed — and the rule is the durable part of the page, not the gap.** What IS shared is the **failure answer**: both doors call the one `failProviderRequest`, which reads `executorFor(provider).classify`, so #191 inherited the 429 without re-implementing it. What is NOT shared is request shaping — the door owns the #139 split, the #156 chain, vision/documents and non-strict tools, which is why #167 left it alone, so a new arm is **per-wire, not a copy of its neighbour** ([[2026-07-30-the-antigravity-arm-is-not-a-copy-of-the-anthropic-arm]]). The rule: a new Provider kind means **two** places, and missing the second is silent on the OpenAI door and unit-invisible — only driving the *other* door catches it
- [[the-wisp-badge-runs-from-the-repo-checkout-not-the-plugin-cache]] — `~/.claude/hooks/statusline-wrapper.ps1` points the wisp badge at the **repo checkout** (`plugins/slot/statusline/wisp-statusline.js`), deliberately, because the plugin cache path is per-version. So a stale `~/.claude/plugins/cache/wisp-router/wisp-slot/<v>/` is **irrelevant to the badge** and `/plugin update` does not change what the statusline runs. Cost a session: the 1.5.0 cache was correctly seen to lack the `status.json` reader, and the wrong conclusion ("the badge won't appear until the user updates") rode in the handoff note as a blocker while the badge was working the whole time. Read the wrapper first to find which file actually runs, then test that file. It exits 0 **silently** unless both `ANTHROPIC_BASE_URL` is set and `$WISP_HOME` exists — an unbridged shell renders nothing, identical-looking to broken
- [[verifying-a-fix-release-needs-the-previous-version-as-a-control]] — "install the new version, bug is gone" proves nothing: most natural checks pass on the **broken** version too, so green means the harness ran, not that the fix shipped. On #183 a *read* check was green on 2.0.38 and 2.0.39 alike — the read never threw, it returned `{}` with exit 0; the bug was in the **write**. Run the identical harness against the **previously published** tarball (`npm i wisp-router@<prev> --prefix …`) and require it to FAIL. Design it around the mutation: touch a *different* row than you seed, and seed unrelated top-level fields so the blast radius shows. Also here: npm can **404 a version its own publish job just succeeded on** — propagation lag, not a broken release; check the job log and `dist-tags`, then retry
- [[a-handoff-cannot-predict-a-queue-state-its-own-last-step-changes]] — a relay leg writes its handoff **before** the next leg runs, so any claim about "what the queue will look like afterwards" is a prediction — and when the leg's own last step **mutates the queue**, it is a prediction written from a state that no longer exists. Leg 6 → 7 shipped both halves in one pass: *"8. Label #197 `ready-for-agent` — last act"* immediately followed by *"then the queue is dry again → `stop: true`, no leg 8"*. Step 8 arms a ticket, so the queue contains exactly what step 8 just added; each half reads as correct alone and only the **ordering** is wrong. Write the stop as an **instruction with its reason**, never as a prediction of queue state. Leg 7 honored the stop because the *reason* outlived the premise (the vsix is packaged, not installed — the extension face has a human step regardless of the label), and pointed the baton at #197 so re-arming costs one command. When an instruction and its justification come apart, prefer the one whose reason still holds; when neither is clear, take the cheapest to reverse — a stall costs one command, an unwanted autonomous full-permission leg costs a review
- [[status-json-is-global-so-it-cannot-observe-another-session]] — `~/.wisp/status.json` is **one file per machine**, rewritten after every bridged turn on the Anthropic door. If *you* are running bridged, your own tool call overwrites it, so reading it to inspect **another** session returns your own snapshot, one second old and entirely plausible-looking. Cost a step while verifying #165. The statusline's model-match guard hides cross-family clobbering from the badge but does **not** stop the write. To verify a session actually reported usage, read the per-session **Claude Code transcript** instead — folding rows by `message.id`
- [[a-bom-in-wisp-config-silently-empties-the-whole-config]] — a UTF-8 BOM at the start of `~/.wisp/config.json` makes Wisp discard the **entire** config (provider, models, effort, the whole Routing map) with **exit 0 and no stderr**: `JSON.parse` throws, `parseObject` swallows it, `parseWispConfig` returns `{}` *above* every field guard. Bites agents because PowerShell 5.1's `Out-File -Encoding utf8` writes a BOM **by default**, so a sandbox `WISP_HOME` seeded from PowerShell reads as empty and looks exactly like a broken feature — it cost a verification pass during the 2.0.38 cut. Check `head -c 3 config.json | xxd` for `efbbbf` before suspecting code. Filed **#181**, pre-existing
- [[harvest-tickets-carry-body-text-blockers-not-native-links]] — the harvest tickets' `## Blocked by` is **prose in the issue body**; the native GitHub dependency links are not set, so GraphQL `blockedBy` returns an **empty list even for a genuinely blocked ticket** (#173 reported empty while three of its four blockers were open). An unattended leg that trusts it will start a ticket whose dependencies have not shipped. Read the body section and cross-check the queue table in [[active-work]]; empty `blockedBy` is *no information*, not *no blockers*
- [[readablestream-error-discards-the-queued-chunks]] — `controller.error()` **empties the queue**, so enqueue-then-error in one tick does NOT model a partial delivery: the reader sees only the error, and a test meant to prove "already delivered ⇒ never retried" silently tests the opposite case. Drive it from `pull()` instead. Tell: `expected 502 to be 200` on a partial-stream test
- [[a-door-commits-its-200-head-before-the-upstream-request-has-run]] — provider streams are async generators, so calling one does NO IO: the doors wrote `writeHead(200)` before the request had fired, making every pre-stream failure a **200 with an empty body** and the 502 branch dead code. `primeStream` (#166) pulls the first event ahead of the head. Tell in a test: `expected 200 to be 502`. **Fixed everywhere by #167** (priming is uniform across all four records) — and that uniformity is what made #168's retry boundary expressible
- [[cc-transcript-rows-are-blocks-not-messages]] — a transcript row is one content BLOCK, not one message: `message.id` / `stop_reason` / `usage` repeat on every row of the same message. Fold by `message.id` first or the file lies three ways — every message looks single-block, `usage` sums N×, and a text-only row appears to violate its own `stop_reason`. Produced a whole false bug report on 2026-07-25
- [[claude-code-can-refuse-a-turn-before-the-bridge-ever-sees-it]] — `Context limit reached` in a bridged session can be a LOCAL Claude Code block that never hit the wire; prove it from CC's own transcript (`~/.claude/projects/<slug>/*.jsonl`) — a ms-scale gap between tool_result and the `<synthetic>` error means no round trip. 2.1.220 also inflates the `/context` Messages row past its own honest headline
- [[advisor-toggle-forks-the-cache-prefix-two-variants]] — advisor mode forks the cached prefix into two variants: Claude Code's auxiliary fork queries (auto-memory extraction, compact, …) replay the conversation WITHOUT the advisor tool (class-gated injection); first fork re-writes ~whole prefix uncached, then each variant re-bills the other's history deltas. Not a user toggle, not a wisp bug. Tickets #158/#159/#160 (all resolved)
- [[buildanthropicmessagesbody-must-not-mutate-caller-rawcontent]] — `buildAnthropicMessagesBody` must replay a *copy* of `rawContent` (strip any inbound `cache_control`); mutating the caller's array lets multi-build flows (advisor base→reviewer→continuation) stack markers past Anthropic's cap of 4 → "Found 5". Regression in `anthropic.test.ts`
- [[anthropic-cache-ttl-flip-busts-the-prefix-mid-session]] — deriving the Anthropic cache TTL from `convo.length` flips 5m→1h between turn 1 and turn 2 of the same session; a TTL change rewrites `cache_control` and busts the server-side prefix cache (2× re-bill on turn 2 of every session). Fix TTL per call path, never from turn count
